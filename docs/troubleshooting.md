# 故障排查

## 更新后证书一直「读取中」、模型与统计不刷新

1.0.17 曾在大数据库上出现历史清理占用写锁、代理启动等待同一写锁的问题。界面又把多个状态读取合并为一次刷新，导致已有模型和证书都无法显示。**1.0.18 已修复该启动阻塞原因。**

1. 在「系统设置 → 关于与更新 → 软件更新」确认版本；界面无法操作时，退出应用，从 [Releases](https://github.com/haxsd/haxsd-byok/releases/latest) 下载新版安装包覆盖安装。
2. 重新打开应用，检查模型数量、证书与接管状态，再发起一次客户端请求并查看「调用」页。
3. 若新版仍出现相同现象，保存应用版本、客户端版本、发生时间和脱敏错误信息，提交 Issue。不要删除数据库、重复生成 CA 或上传整个数据目录。

这是已修复的后端阻塞原因；界面的请求超时和局部刷新能力仍有改进空间。安装、备份和恢复见 [用户指南](./user-guide.md)。

## Devin 接入后找不到安装、无法写入或没有请求

接入完成需要同时满足：Devin 的服务地址与兼容补丁都已写入，本机网关显示已监听。只保存模型或打开网关并不算接通。

### 找不到 Devin，或自定义安装目录没有生效

- 先安装并完整启动一次 Devin，让自动探测能读到默认数据目录和扩展文件，再点「重新检查」。
- 安装位置不是默认值时，展开「高级」，在「Devin 安装目录」填安装根目录，或其中 `extension.js` 的完整路径；「Devin 设置文件路径」可填 Devin 数据目录或 `User\settings.json`。两处都必须填绝对路径且实际存在；无效路径会明确报错，不会静默换回别的安装。
- Devin 升级可能改变扩展哈希。当前版本只支持 Devin `3.11.216`；状态显示“版本暂不支持”或哈希不匹配时，不要手工替换或强行覆盖文件，先保留原文件并反馈版本信息。

### 保存提示没有默认模型

启用网关保存前，必须在「默认模型」选择一项已启用的标准映射。只添加映射不等于设置默认模型，上下文压缩映射也不能作为默认模型。账号登录、套餐与额度仍由 Devin 管理，不需要在本应用里再次登录。

### 写入被拒绝或恢复失败

- 写入和恢复前完全退出 Devin：关闭主窗口不等于退出，还要结束托盘与后台进程。仍在运行时文件会被占用，写入会失败。
- 设置文件只有一部分端点、JSONC 无法解析、文件不是 UTF-8、被其他工具改过，或被本应用写入后又改过时，保护机制会拒绝写入或恢复。先回到 Devin 修正配置，或走客户端自己的修复／重装流程；不要用旧备份覆盖新版本。
- 显示「配置冲突」时，先检查该文件是否由其他 BYOK 或路由工具接管。本应用不会覆盖其他工具写入的配置。

### 网关未监听或端口被占用

- 端口在保存并重启本应用后才开始监听。默认使用 `43110`–`43112`，被其他进程占用时保存会失败或改用其他端口；换一组未被占用的端口再保存。
- 改过端口后，需要保存、重启本应用、完全退出 Devin，再重新写入接入配置并启动 Devin。只改其中一侧会让客户端继续请求旧地址。
- 网关只监听 `127.0.0.1`；不要把地址改成机器名、局域网 IP 或外部代理。

### Devin 里仍然没有调用记录

依次检查：网关已监听；默认模型与请求的模型映射都已启用；Devin 已完全退出并重新启动；服务地址和兼容补丁都显示已写入；实际请求的模型 UID 与映射一致；若设置了控制令牌，Devin 发出了同一个值。最后在 Devin 里发一条新消息，而不是只看旧会话。

### 新会话提示额度不足

登录、套餐、免费额度和新会话资格由 Devin 官方服务决定，本应用不会伪造或绕过。普通账号仍按 Devin 官方套餐使用；新会话出现 “You ran out of free credits” 表示官方额度不足，不是本机网关断流。已创建且仍能发送消息的会话可能仍可由本机模型回答；需要新会话时，请换用仍有官方访问资格的账号或按 Devin 官方方式订阅。

## Codex 接入后客户端没有自配模型，或第一轮就报错

现象：Codex 页显示网关已运行，但客户端里看不到模型；或客户端本地任务一开始就报错。

先分清两种状态：「网关已监听」只说明本机网关在运行，客户端是否改用它取决于你有没有点「应用到 Codex」。列表只出现「待应用配置」时，点应用后重新打开客户端或新建会话。

应用成功但仍然报错时，检查这几项：

- 配置目录填错：客户端用的是自己的 `CODEX_HOME` 或用户目录下的 `.codex`，页面里填写的必须是同一个目录。
- 提示不支持的托管工具：本次接入只提供本地工具桥接和官方托管搜索的关闭开关，客户端额外开启的托管能力不被支持；先撤销接管、应用最新配置再试。
- 工具被审批或沙箱拒绝：在原版客户端处理，本应用不会绕过或放宽审批与沙箱。
- 改了模型的服务商配置（地址、Key、模型 ID）后旧会话报错：撤销接管、重新应用并**新建会话**，不要在同一条会话里继续。

界面与完整步骤见 [Codex 接入](./codex-go-live.md)。

## Claude 网关未监听、401 或客户端不生效

先确认三件事：网关已启用并保存、页面显示「已监听」、对应客户端是在应用接管之后重新打开的。网关由本应用进程提供，退出应用后端口不再监听。

### 网关未监听或端口被占用

- 「未启用」：网关开关没打开。先在网关里选默认模型，再启用并保存。
- 「未监听」但已启用：端口被本应用其它网关或别的程序占用。保存时会被拒绝，不会留下「已保存、未监听」的状态；换一个端口保存即可。
- 改过端口后状态会显示「配置已过期」：CLI 的 `settings.json` 与 Desktop 的 profile 里仍是旧地址，重新应用接管即可；Desktop 还要先完全退出。
- 网关只监听 `127.0.0.1`，不要把它暴露到局域网，也不要把网关地址填成机器名或外部 IP。

### 401 / 未授权

401 表示请求带的 Bearer 令牌与网关当前令牌不一致，通常是轮换后客户端还在用旧值。

1. 在「Claude」页复制当前访问令牌。
2. 重新应用对应客户端的接管；Claude Code 需要重新打开。
3. Claude Desktop 正在运行或已接管时，服务端会拒绝轮换：先完全退出 Desktop，已接管再撤销 Desktop 接管，然后轮换。CLI 已接管时，轮换会自动把新令牌写回 `settings.json`。
4. 用户环境变量里的同名键也会影响从本应用之外启动的 Claude Code；页面只提示、不阻断，按提示清理后再启动客户端。

订阅账号的 OAuth 授权是模型来源，不是网关令牌；不要把订阅 access token 填进客户端的网关鉴权。

### Claude Code CLI 显示「未检测到」

配置目录、`settings.json` 和 `claude` 可执行文件都不存在时才是「未检测到」。先安装 Claude Code 并运行一次，再回到页面应用。

配置目录或 CLI 已存在、只是还没有 `settings.json` 时，应用会新建该文件。设置了 `CLAUDE_CONFIG_DIR` 时，页面写的目录必须和客户端实际读取的目录一致，否则会出现「应用成功但客户端不生效」。

### 显示「受管配置」

以下任一来源存在时，`settings.json` 不再是唯一配置来源，本应用不会改写它：

- `%ProgramFiles%\ClaudeCode\managed-settings.json`
- 同目录下 `managed-settings.d\*.json`
- 注册表 `HKLM\SOFTWARE\Policies\ClaudeCode` 或 `HKCU\SOFTWARE\Policies\ClaudeCode` 里的 `Settings`

需要管理员调整或移除策略，或按组织要求手工配置。不要直接改 `Program Files` 下的文件来绕过策略。

### Claude Desktop 写入被拒绝或接管不生效

- 状态「运行中」时服务端会拒绝写入。只关窗口不算退出，要从托盘退出或用任务管理器结束进程，再应用或撤销。
- 应用后重新打开 Claude Desktop。仍不生效时先完全退出再启动，再看「配置来源」与冲突条目；受管状态只能手工配置。
- 状态为「机器策略」（`HKLM\SOFTWARE\Policies\Claude`）或「用户策略」（`HKCU\SOFTWARE\Policies\Claude`）时，本应用不写 profile，也不写组策略；在 Claude Desktop 里打开 Developer → Configure Third-Party Inference 逐项填写。

### 出现 `[1m]` 或 `unrecognized_model`

Claude Code 会在模型 ID 后追加 `[1m]` 表示 1M 上下文变体，模型库里没有这个独立模型。网关会先去掉后缀再解析。

如果客户端仍提示 `unrecognized_model`，依次检查：应用是当前版本；接管里选的模型还在模型库；重新应用接管并重启 Claude Code。仍不行时，把对应的 Sonnet / Opus / Haiku 别名改成一个明确存在的模型，不要只依赖默认模型回落。

### 显示「配置已过期」

状态「配置已过期」表示客户端文件仍是本应用写下的那一份，但网关端口、访问令牌或模型映射已经变了，客户端指向旧值。

- 重新应用对应客户端的接管即可；Desktop 还要先完全退出。
- 改端口或模型映射后、轮换令牌后都可能出现这个状态。它不算配置冲突，不要点「撤销接管」再重来，直接重新应用。
- 重新应用后仍显示过期：检查网关是否已监听、默认模型是否还在模型库，以及页面是否有未保存的改动。

### 应用退出后接管失效

正常退出应用（从托盘选择退出）会撤销 CLI 接管；Claude Desktop 未运行时也撤销 Desktop 接管。Claude Desktop 正在运行时服务端无法改写它的 profile，接管保留，下次启动后重新应用。

- 进程被强制结束或崩溃时不会执行退出清理，接管文件保留。下次启动网关会重新监听同一端口，通常可以直接继续使用；改过端口、令牌或模型映射时按「配置已过期」重新应用。
- 退出应用后网关停止，未撤销的 Desktop 接管会连接失败；让应用保持运行，或下次启动后重新应用。
- 想手工还原客户端文件，点「撤销接管」；不要手工删除 `settings.json` 里的键或 Desktop 的 profile。

## Cursor 报 `Failed to establish a socket connection to proxies: PROXY 127.0.0.1:<BYOK 代理端口>`

### 现象

提交聊天后 Cursor 报错：

```
[internal] Failed to establish a socket connection to proxies: PROXY 127.0.0.1:<端口>
```

同一时刻 `renderer.log` 中多个子系统（pricing、privacy mode、metadata sync、插件市场等）报同一条错误。此时 BYOK 本体、管理端口、证书与模型配置均正常，用 `curl` 直接测该代理端口也能连通。

### 成因

底层是 Windows 回环地址偶发 SYN 丢失或延迟。Node 的 libuv 在 Windows 上对回环地址显式关闭 SYN 重传（`src/win/tcp.c` 中 `MaxSynRetransmissions = TCP_INITIAL_RTO_NO_SYN_RETRANSMISSIONS`），第一发 SYN 未被及时处理即失败，耗时约等于 `MinRto`（约 300ms）。Cursor 基于 Node/Electron，因此把一次底层抖动放大成大面积硬错误；而 `curl`（schannel）与 .NET 会重传 SYN，同样的抖动下它们表现正常，容易误判为「端口没问题」。

### 处理

1. 在 BYOK 设置页把代理端口换成另一个未被占用的端口并重启 BYOK，Cursor 的 `http.proxy` 会自动跟随。
2. 若复发，检查 Npcap 驱动状态（`Get-Service npcap`）；重载驱动（管理员执行 `sc stop npcap` / `sc start npcap`）可清掉卡住的运行时状态。
3. 自检必须用 Node 并发探测回环端口；`curl` 和 .NET 会重传 SYN，暴露不出该问题。

### 状态与注意

- 可恢复，但根因尚未最终确认（主要嫌疑是较老版本的 Npcap 与当前 Windows 版本的组合）；改端口不属于已验证的修复手段。
- 不要把 Cursor 的 `http.proxy` 指向 Clash 等外部代理来绕开该错误，那会使 BYOK 的本地接管失效。
- 详细证据链、时间线与复现步骤见本机记录（未纳入仓库）。

## Cursor 里看不到官方模型，或账号显示成「本地账号」

### 现象

模型列表里只有模型库里的模型，看不到官方模型；Cursor 的账号菜单显示 `cursor@ai.com` / “Cursor Local”。

### 成因

客户端在用本应用注入的本地账号，或者干脆没有登录。本地账号不是官方账号，携带它的请求会被官方接口拒绝（401），官方模型目录抓取失败后，列表就只剩本机的模型。这不是官方模型被移除，也不是开关没生效。

另外，「本地」模式本来就只列模型库里的模型——要同时用官方模型，需要「混合」模式。

### 处理

1. 打开「Cursor」页，切到「混合」。这一步会清除本应用注入的本地账号，并结束正在运行的 Cursor。
2. 重新打开 Cursor，退出登录后用自己的账号登录。
3. 回到「Cursor」页确认这两行：「Cursor 账号：你的账号（…）」和「官方模型目录：正常」。之后模型列表里会同时出现官方模型和你的模型。

「官方模型目录」显示失败时，页面会给出原因：401 通常是账号未登录或登录已过期；网络类原因重复出现时先检查本机到官方服务的连通性。

## 混合/官方模式里官方模型报错或超时，本机模型却正常

### 现象

- 官方模型（或整条 Cursor 请求）报错、超时、连接失败；同一时间本机模型一切正常。
- 出网方式在设置页里是「直连」。

### 成因

「直连」是**全局**的：它同时关掉转发官方请求那条路的代理。官方模型要出我们这一跳到境外
上游，直连下必然连不上；本机（国内）模型不受影响，所以看起来像"只有官方模型坏了"。

### 处理

- 要用官方模型：把出网方式改成「跟随系统代理」（推荐，把分流交给代理软件的规则）或
  「自定义」并填一个能出境的地址。
- 只用本机模型：保持「直连」即可，页面不会再提示。
- 顺带注意：「自定义」只支持一个地址、不按域名分流；填了境外节点，国内模型的请求也会绕出去。

## `cargo test --workspace --all-targets` 在桌面 crate 上失败（`0xc0000139`）

### 现象

`cargo test --workspace --all-targets` 走到最后一个目标时失败：

```
Running unittests src\lib.rs (target\debug\deps\haxsd_byok_desktop-<hash>.exe)
error: test failed, to rerun pass `-p haxsd-byok-desktop --lib`
  process didn't exit successfully: ... (exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND)
```

其余所有目标（`cursor-server` 的 11 个套件、`semble-*`）全部通过，失败只发生在
`haxsd-byok-desktop` 的单元测试二进制上。

### 已排除的原因

| 假设 | 证据 |
| --- | --- |
| 构建产物过期/损坏 | `cargo clean` 后全量重编（23.8 GiB 清空重建），新二进制仍然报同一个错 |
| 重链接即可 | 删掉该 exe 触发单独重链接，哈希变化，报错不变 |
| 缺少 `libmcfgthread-2.dll` | 用 C 写探针 `LoadLibrary` + `GetProcAddress`，8 个待解析符号全部返回有效地址；exe 所在目录放置该 DLL 也无效 |
| 缺别的 DLL | 逐个核对导入表：KERNEL32 203 项、ntdll、user32、ucrtbase 系、crypt32 等 0 缺失 |
| PATH / 工作目录 | 净化 PATH、换工作目录、把 DLL 放到 exe 旁，全部一致报错 |
| PE 导入表损坏 | `objdump -p` 的导入描述符、导入名表、导出表结构均正常；那 8 个名字在当前 DLL 里都存在且序号一致 |

### 已知线索

该 exe 的导入 hint 序号比当前 DLL 的导出序号小 1~2（例如 import hint 25 / DLL 里是 26），
说明链接它的静态库是在另一套 MCF 头文件下编出来的。按名字解析本应忽略 hint，
所以这解释不了报错，但这是目前唯一未对齐的地方。

### 结论：本机 GNU 工具链的问题，不是代码问题

同一份代码、同一个测试二进制，在 CI 的 MSVC runner 上正常加载并运行：

```
running 1 test
test startup::tests::fatal_report_includes_the_complete_error_chain ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

（CI 运行 `35567454874`，`Desktop Rust (windows-latest)` 的
「Run the desktop unit tests on MSVC」步骤。）

Windows 桌面单元测试现已在 CI 中默认执行，不再依赖仓库变量启用。检查具体版本时仍应核对该步骤实际执行结果，不能把编译检查或被跳过的测试视为通过。

### 处理

- Windows 开发与验证使用 MSVC 工具链及对应的 Visual Studio Build Tools。已经安装该工具链时，可显式运行：

```powershell
cargo +stable-x86_64-pc-windows-msvc test --locked --workspace --all-targets
```

- GNU 环境的原生依赖错误应单独定位；排除桌面后的测试只能证明被执行的部分，不能代替桌面测试。
- 前端验证运行 `npm --prefix apps/desktop run check`，包含类型检查、行为测试与生产构建。
