## 已修复源码：插件路径可指向父目录

位置：[plugin/data.rs](../server/src/plugin/data.rs)。原组件校验允许目录别名，插件配置删除及数据读取/写入直接把传入的插件 ID 拼接到数据目录。目录别名因此可越过插件自身目录边界，影响其他插件配置或运行文件。这是优先级最高的破坏性路径问题。

本轮在任何文件操作之前拒绝尾部句点，覆盖当前目录、父目录、纯句点和 Windows 尾部句点别名，并增加单元和临时目录回归验证。测试覆盖读取、写入、删除拒绝，以及原有正常插件数据和父目录标记不受影响。旧实现的测试失败已观察到；Windows 的非删除式目录探针确认纯句点名称指向现有目录，补充回归也在首轮修复中失败。验证中未对真实插件目录执行危险请求。

HTTP 路由如何处理编码路径的攻击链没有在实际服务上验证，因此不声称已经重现远程利用。源码数据层的路径边界缺陷与修复已确认。另有管理接口授权加固需求，见下文。

## 待修复：稳定性与数据正确性

### P2-1：管理请求没有默认超时，刷新又依赖全部接口成功

位置：[api.ts:578](../apps/desktop/src/shared/api.ts#L578)、[appStore.ts:143](../apps/desktop/src/shared/store/appStore.ts#L143)。

`fetch` 没有默认截止时间，刷新通过 `Promise.all` 等待 10 个接口后才更新任何数据。任一接口迟迟不返回，`busy` 就一直为真；任一接口报错，即使模型、统计等接口正常，它们也不会更新。模型删除、创建和编辑之后也依赖该完整刷新，容易造成“操作已成功，界面却像没成功”。

**证据**：隔离探针让证书状态请求悬挂，刷新保持忙碌；让它拒绝，模型请求虽成功，模型数量仍为初始值。1.0.18 修掉了本次后端锁等待原因，但界面的此种脆弱性仍然存在。

建议：普通状态读取增加截止时间，保留调用者取消信号；不同模块独立提交结果并明确显示各自错误。长耗时安装、模型测试等操作应有各自的超时策略，不能统一套短超时。模型变更优先使用变更接口的返回结果更新列表。

回归验证：悬挂一个状态请求时，其余模块仍显示数据，刷新能结束；单模块失败显示失败，不显示假空数据；模型变更成功后，即使其他状态读取失败也能显示变更。

### P2-2：并发刷新可让旧结果覆盖新结果

位置：[appStore.ts:143](../apps/desktop/src/shared/store/appStore.ts#L143)。

CA 检查轮询、离线重试、手动刷新和模型操作后刷新可能重叠。当前没有请求版本判断，最后返回的结果覆盖整份状态；先结束的请求还会提前清掉 `busy`。

**证据**：隔离探针先启动旧刷新，再启动新刷新；新结果先返回后，旧结果仍能覆盖它。新请求结束时，旧请求尚未结束，`busy` 已经变为假。

建议：给刷新添加版本或取消机制，限制旧结果写入；忙碌状态按有效在途请求计算。模型修改也应使修改前的列表请求失效，单纯给刷新编号仍需验证变更竞态。

回归验证：反转响应顺序，最终状态仍是新结果；修改模型期间旧 GET 返回，不能恢复旧配置。

### P2-3：异常退出清理助手使用自己的 PID，误判为新实例接管

位置：[desktop.rs:357](../apps/desktop/src-tauri/src/desktop.rs#L357)、[desktop.rs:390](../apps/desktop/src-tauri/src/desktop.rs#L390)、[cleanup.rs:40](../server/src/local_app/cleanup.rs#L40)。

助手作为独立进程启动，但调用 `cleanup_after_exit` 时传入自己的进程编号；实例归属记录中存的是主应用编号。主应用仍持锁时，这两个编号不同，助手便认为另一个实例接管而退出。

**证据**：代码调用链与启动参数已确认。现有测试中持锁者与等待者处于同一进程，未覆盖真实父子进程的编号差异。未在用户客户端上执行强杀测试。

影响：主应用崩溃或被强制结束时，预期后台清理可能没有执行，Cursor 会继续指向已无监听的代理，直到应用下次启动清理。正常退出路径另有清理，不能据此判断正常退出也失效。

建议：启动助手时显式传递主应用 PID，助手校验参数后使用该值；保留新实例接管时停止清理的保护。

回归验证：用临时数据和独立父子进程测试父进程结束、新实例抢先启动、正常退出三条路径，不能触碰实际 Cursor 配置。

### P2-4：崩溃留下的“运行中”记录缺乏收尾，详情可永久保留

位置：[retention.rs:45](../server/src/store/retention.rs#L45)、[retention.rs:72](../server/src/store/retention.rs#L72)、[overview.rs:37](../server/src/store/overview.rs#L37)。

进程中断后，数据库中的调用/追踪可能仍为 `running`，没有启动收尾流程。详情清理排除所有 `running` 调用与追踪，因此旧记录仍能长期钉住内容；调用数量与成功/失败统计也排除这些行。一个较新的遗留 `runs` 记录还可能让整次清理跳过，最长影响 3 天。

**证据**：内存 SQLite 执行生产清理 SQL，过期 `running` 调用的详情保留；同一行改为结束状态后详情才清理。已复核启动路径和状态终结位置，未对真实数据改状态。

建议：确认旧实例已经结束后，识别遗留运行并标记中断，保留检查点恢复能力；不要把未知上游用量编造成已知值。将清理保护与实际活动生命周期对应，避免一个遗留运行挡住所有无关详情的清理。

回归验证：崩溃后重启，遗留调用显示为中断，详情按期限清理；真实活动调用不会被误终结，检查点仍可恢复。

### P2-5：首页范围查询失败后，旧数据仍配上新范围标签

位置：[HomePage.tsx:88](../apps/desktop/src/features/home/HomePage.tsx#L88)、[HomePage.tsx:117](../apps/desktop/src/features/home/HomePage.tsx#L117)。

范围请求只有 `then` 和 `finally`，没有失败处理；开始新请求时也没有为旧结果记录其所属范围。选定范围改变后，新查询失败，旧 `rangeOverview` 仍用于指标与图表，但界面范围标签已经改变。

**证据**：代码链确认，属于静态验证；未在实际窗口制造接口失败。

建议：结果与查询范围、模型筛选一起保存，失败时显式显示错误与重试；如果保留旧数据，应同时保留旧范围说明。

回归验证：先成功查询 A，再查询 B 并令其失败，不能把 A 的数据标成 B。

## 需要设计决策的加固项

1. **本机管理服务的信任边界。** 管理 API 没有独立授权，模型列表会返回用于编辑的 Key，插件资源导出也包含账号凭据。CORS 允许本机及私网来源，它不能替代接口身份验证。当前桌面通常绑定回环地址，不能把它当成可安全暴露给局域网的管理服务。建议独立管理令牌、更窄的来源策略和凭据展示/导出策略；这涉及桌面与 API 协议，需要整体设计。[control/mod.rs:117](../server/src/control/mod.rs#L117)、[control/mod.rs:279](../server/src/control/mod.rs#L279)、[configuration.rs:125](../server/src/model/configuration.rs#L125)、[plugin/registry.rs:789](../server/src/plugin/registry.rs#L789)
2. **协议错误的重试成本。** 当前所有 `RunFailure::Protocol` 都可重试，最多额外重试 8 次。随机生成错误可能被重试改善，但服务商固定返回不兼容协议时会重复耗时或产生用量。建议区分可恢复和固定格式错误，限制后者重试。[model_cycle.rs:377](../server/src/run/model_cycle.rs#L377)、[model_retry.rs:8](../server/src/run/model_retry.rs#L8)
3. **宿主恢复记录的归属。** 服务端直接信任客户端提交的恢复记录，再校验文件与哈希；它证明“文件与这份记录相符”，不能独立证明“记录由本实例应用补丁时生成”。写入内容仍受干净宿主文件校验约束。建议服务端保存记录并按规范化路径查找，提高授权边界的可靠性。[control/devin.rs:119](../server/src/control/devin.rs#L119)、[host_patch.rs:134](../server/src/devin/host_patch.rs#L134)

这些是代码确认的边界与策略问题，本轮没有执行攻击验证，也不将它们描述为已经发生的凭据泄露。

## 排除的误报与保留的限制

- “选择 7 天/30 天会清除已应用的模型筛选”不成立：`selectPreset` 没有修改 `appliedModels`，请求仍使用原筛选。
- 未确认异常图片 blob ID 有真实可达输入路径；不能仅因 GC 解析可能抛错便认定普通客户端能永久破坏清理。
- 图表主题依赖、被缓存页面的重新进入行为及全部长尾控件仍需要专门交互走查，不据推测报告为已确认 bug。
- 1.0.18 的批量清理、未变化代理端口不再等待写锁、追踪附件索引修复均已存在，不重复列为待修复项。

推荐顺序：先补刷新与异常退出的回归覆盖，再修复 P2-1～P2-4；之后修复范围数据反馈与操作体验，最后设计管理授权和凭据边界。
